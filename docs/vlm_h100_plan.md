# H100 单卡 VLM 推理服务方案

## 1. 目标与约束

- 部署环境：单机单卡 NVIDIA H100 80G
- 运行位置：代码最终运行在云端服务器，本地开发机不做 LLM 推理调试
- 服务对象：同一台机器上的另一个进程
- 服务职责：提供稳定的 VLM 推理接口，支持图像 + 文本输入，返回结构化文本结果
- 使用模型：`Qwen3.5-27B`
- 服务监听：`127.0.0.1:8972`
- 输入方式：支持本机路径和 Base64
- 重点指标：
  - 启动后常驻显存内，不频繁卸载模型
  - 优先保证稳定性和吞吐，其次再做极致低延迟
  - 接口简单，便于本机其他进程直接调用
  - 方案可从 MVP 平滑演进到生产可用

## 2. 总体建议

推荐采用：

- 推理引擎：`vLLM`
- 模型：`Qwen3.5-27B`
- 服务封装：`FastAPI`
- 进程通信：`127.0.0.1 HTTP`
- 部署方式：`systemd` 或 `supervisord` 拉起单服务
- 监控：Prometheus 指标 + 结构化日志

这个组合的原因：

- `vLLM` 在服务化、连续批处理、吞吐和 OpenAI 风格接口兼容性上比较成熟
- 对单卡大显存场景友好，适合作为常驻推理后端
- `FastAPI` 适合补齐鉴权、输入校验、任务路由、健康检查和业务定制
- 同机调用下，`127.0.0.1` 已经足够快，调试成本最低

## 3. 模型选择

当前模型已经确定为：

`Qwen3.5-27B`

当前策略：

- 不再做模型选型比较，后续直接围绕 `Qwen3.5-27B` 完成工程实现
- 第一版优先保证“能稳定加载、能稳定提供接口、能完成图文推理”
- 由于场景是自用低并发，性能策略优先简单稳定，而不是极限吞吐
- 云端已确认运行环境：
  - Python `3.11.14`
  - conda 环境 `vllm`
  - `torch 2.10.0`
  - `transformers 4.57.6`
  - `vllm 0.15.1`
  - `fastapi 0.128.2`
  - `uvicorn 0.40.0`
  - Driver `580.65.06`
  - CUDA `13.0`

推理框架策略：

- 默认优先尝试 `vLLM`
- 如果 `Qwen3.5-27B` 在目标服务器上的 `vLLM` 兼容性、稳定性或多模态支持不满足需求，再切到 `transformers` 直连

这意味着第一阶段的工作重点从“模型选型”转为“工程落地”。

## 4. 服务架构

建议拆成两层：

1. `Gateway/API 层`
2. `Inference Engine 层`

### 4.1 Gateway/API 层

职责：

- 接收本机进程请求
- 校验参数
- 做图片载入与格式转换
- 统一 prompt 模板
- 请求限流和排队
- 结果后处理
- 输出日志、指标、trace id

建议技术栈：

- `FastAPI`
- `Pydantic`
- `uvicorn`

### 4.2 Inference Engine 层

职责：

- 模型加载
- tokenizer / processor 管理
- batch 调度
- 生成参数控制
- 显存管理

建议实现：

- 优先直接使用 `vLLM` 服务能力
- 如果业务需要强定制，再在 Python 进程内封装 `vLLM` engine

## 5. 进程通信设计

### 推荐方案：本机 HTTP

监听：

- `127.0.0.1:8972`

优点：

- 对调用方最友好
- 调试、压测、健康检查都方便
- 可无缝兼容 curl、Python requests、Go/Java SDK

### 可选方案：Unix Domain Socket

适合场景：

- 明确只允许同机访问
- 希望减少网络栈开销
- 希望用文件权限控制访问

结论：

- 第一版先用 `127.0.0.1 HTTP`
- 稳定后如确实需要，再增加 UDS 支持

## 6. API 设计建议

建议至少提供以下接口：

### `GET /healthz`

用途：

- 进程存活检查
- 不校验模型可用性

返回示例：

```json
{"status":"ok"}
```

### `GET /readyz`

用途：

- 模型是否已完成加载
- tokenizer / processor 是否可用

返回示例：

```json
{"status":"ready","model":"Qwen3.5-27B","backend":"vllm","loaded":true,"error_message":null}
```

### `POST /v1/chat/completions`

建议兼容 OpenAI 风格，方便调用方快速接入。

请求示例：

```json
{
  "model": "Qwen3.5-27B",
  "messages": [
    {
      "role": "user",
      "content": [
        {"type": "text", "text": "请描述图片中的主要内容"},
        {"type": "image_url", "image_url": {"url": "file:///tmp/demo.jpg"}}
      ]
    }
  ],
  "temperature": 0.1,
  "max_tokens": 512
}
```

### 可选补充接口

- `POST /v1/infer`
  - 提供更轻量的业务定制接口
- `GET /metrics`
  - 暴露 Prometheus 指标

## 7. 输入数据建议

建议支持三种图片输入方式：

1. 本机文件路径
2. Base64
3. HTTP/HTTPS URL

但如果“调用方与服务在同机”是确定前提，首版最建议：

- 只支持 `本机文件路径` 和 `Base64`

原因：

- 避免服务侧额外拉远程图片，减少不可控网络问题
- 文件路径模式性能最好，也最适合同机进程协作

建议约束：

- 对单图大小设上限，例如 `20MB`
- 对分辨率设上限，避免极端大图打爆前处理耗时
- 限制每次请求图片数量，例如 `1-8 张`

## 8. 显存与性能规划

H100 80G 的关键不是“能不能跑”，而是“显存怎么分配更稳”。

### 8.1 首发建议

当前仓库已经按 `Qwen3.5-27B + BF16` 的方向实现最小版本，后续的性能与稳定性优化都应围绕这一前提展开。

建议思路：

- 不要把显存吃到极限
- 预留显存给图像预处理、中间张量和 KV Cache
- 在真实服务器上根据压测结果再决定是否收紧 `max_tokens`、图片大小和并发数

实践上建议保留 `10%~20%` 安全余量。

### 8.2 吞吐优化方向

核心手段：

- 连续批处理
- 合理的 `max_num_seqs`
- 合理的 `max_model_len`
- 限制 `max_tokens`
- 输入图像尺寸标准化

### 8.3 延迟优化方向

如果调用方是交互型场景，建议：

- `temperature=0` 或低温
- 收紧 `max_tokens`
- 优先控制 prompt 长度
- 减少无效图片分辨率

### 8.4 模型长度建议

第一版不要把上下文长度开得太夸张。

建议：

- 先按业务真实需要设置，例如 `4k ~ 8k`
- 长上下文会明显抬高 KV Cache 压力，降低并发上限

## 9. 并发与队列策略

单卡服务必须有排队机制，不能让请求直接无上限打到 GPU。

建议：

- 网关层维护有限队列
- 设置最大并发请求数
- 达到阈值时快速返回 `429` 或业务错误码

建议配置：

- `max_concurrency`：2 到 8，按模型大小压测决定
- `queue_size`：32 到 256
- `request_timeout`：30s 到 120s

原则：

- 先稳住 tail latency
- 再逐步提高吞吐

## 10. 可靠性设计

### 必要能力

- 启动预热
- 模型加载失败自动退出
- 请求超时控制
- OOM 保护
- 结构化错误码
- 健康检查

### OOM 防护建议

- 限制单请求图片数
- 限制单请求最大输出 token
- 限制上下文长度
- 大图统一 resize
- 队列满时拒绝，而不是继续堆积

如果出现 OOM：

- 记录触发请求参数
- 返回可识别错误码
- 必要时触发进程重建

## 11. 日志与监控

建议至少采集以下指标：

- 请求总数
- 成功率
- 平均延迟 / P95 / P99
- 输入 token 数
- 输出 token 数
- 图片张数
- 队列等待时间
- GPU 显存占用
- GPU 利用率
- OOM 次数

日志建议使用 JSON 结构化格式，至少包含：

- request_id
- client_pid 或调用方标识
- model
- image_count
- prompt_len
- output_tokens
- latency_ms
- queue_wait_ms
- error_code

## 12. 安全与访问控制

因为默认只给同机进程调用，安全重点不是公网防护，而是避免被本机其他无关进程滥用。

建议：

- 只监听 `127.0.0.1`
- 如需更严格控制，可切换到 `Unix Domain Socket`
- 加一个简单的本机 token 校验
- 限制允许访问的图片目录
- 禁止任意读取系统文件路径

尤其注意：

- 如果支持 `file://` 路径，要做白名单目录校验
- 不要让任意调用方借接口读取宿主机敏感文件

## 13. 部署建议

### 13.1 目录结构建议

```text
vlm_server/
  app/
    api/
    core/
    engine/
    schemas/
    services/
  configs/
  scripts/
  tests/
  docs/
```

### 13.2 关键配置项

建议放到环境变量或配置文件：

- `MODEL_NAME`
- `MODEL_PATH`
- `HOST`
- `PORT`
- `MAX_CONCURRENCY`
- `QUEUE_SIZE`
- `MAX_INPUT_IMAGES`
- `MAX_IMAGE_BYTES`
- `MAX_OUTPUT_TOKENS`
- `MAX_MODEL_LEN`
- `LOG_LEVEL`

### 13.3 部署方式

推荐 `systemd`：

- 开机自启
- 异常自动拉起
- 日志易于接入

### 13.4 开发与调试约束

- 本地环境主要用于写代码、补接口、静态检查和轻量测试
- 不把“本地能跑通完整模型推理”作为开发前提
- 涉及真实模型加载、显存占用、吞吐和稳定性的验证，统一在云端 H100 服务器上完成

## 14. 建议的实施阶段

### Phase 1: MVP

目标：

- 跑通单模型常驻服务
- 提供 `/healthz`、`/readyz`、`/v1/chat/completions`
- 支持单图 + 文本输入
- 同机 Python 调用方可稳定访问

当前状态：

- 已完成
- `run_server.sh` 与 `run_client.sh` 已验证可正常工作
- 本地路径和 base64 图片输入链路已跑通

### Phase 2: 稳定性增强

目标：

- 增加队列、限流、超时、错误码
- 增加 metrics 和结构化日志
- 做基础压测

当前状态：

- 尚未完成
- 这是下一阶段最值得优先推进的工作

### Phase 3: 性能优化

目标：

- 调整 batch 参数
- 优化图像预处理
- 对典型业务 prompt 做模板和输出约束

当前状态：

- 尚未开始
- 应放在稳定性能力补齐之后推进

### Phase 4: 业务增强

目标：

- 多图输入
- 流式输出
- 任务模板化
- 业务级鉴权和审计

## 15. 首版落地推荐配置

如果目标是尽快上线一个可靠版本，建议：

- 模型：`Qwen3.5-27B`
- 精度：`BF16`
- 服务：`vLLM + FastAPI`
- 通信：`127.0.0.1:8972`
- 接口：OpenAI 风格 `/v1/chat/completions`
- 图片输入：本机路径 + Base64
- 并发策略：先单卡低并发，再逐步增加保护能力
- 观测：先补请求日志、错误结构和超时控制，再补 metrics

## 16. 不建议一开始就做的事

- 一上来就把并发放开而没有保护
- 一开始就支持远程 URL 拉图
- 没有排队和限流就直接开放并发调用
- 把上下文长度和最大输出 token 开得很大
- 没有 metrics 和 request_id 就直接压测

## 17. 最终结论

对于“单机 H100 80G、同机进程调用”的场景，最稳妥的路线是：

- 先做一个 `vLLM + FastAPI` 的两层服务
- 围绕已确定的 `Qwen3.5-27B` 完成稳定化
- 先用 `127.0.0.1 HTTP` 暴露 OpenAI 兼容接口
- 用低并发、输入约束和逐步补齐的保护能力保证稳定性
- 完成压测后，再决定是否升级到更大模型或更复杂通信方式

这是一个风险、实现成本和可扩展性比较平衡的方案。
